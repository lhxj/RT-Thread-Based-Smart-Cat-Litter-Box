# 基于 RT-Thread 的智能猫砂盆

## 一句话定义

这是一个运行在 HC32F460 + RT-Thread 上的智能猫砂盆控制系统 MVP，重点不在“功能堆叠”，而在于把自动清理流程整理成一个具备显式状态机、安全联锁、故障恢复、关键告警和本地自治能力的嵌入式控制样机。

## 项目目标与 MVP 边界

### 目标

- 把“能动起来的 Demo”整理成“可解释、可观察、可恢复”的控制系统最小版本
- 在本地完成核心控制闭环，不把 MQTT 当成唯一控制入口
- 让状态、故障、联锁和恢复路径都能被稳定演示
- 让项目适合秋招面试时讲述设计思路和工程取舍

### 当前 MVP 明确覆盖

- 显式状态机驱动清理流程
- 占用保护和满仓禁启
- 清理超时 / 满仓 / 保护触发等关键故障路径
- 本地 OLED / 串口 / finsh 可观察性
- 最小 MQTT 状态上报和远程触发

### 当前 MVP 明确不做

- AI、多猫识别、复杂 App、全平台联动
- 新传感器接入和复杂硬件扩展
- 更复杂的故障分类体系
- 大规模协议重构和架构重写
- 闭环电机控制、编码器反馈、电流检测等增强型执行器控制

设计上的核心取舍是：先把“状态可解释、安全可证明、故障可恢复、本地可自治”做好，再谈体验和功能扩展。

## 当前已实现的核心能力

- 自动清理主流程：占用检测、离开确认、清理延时、正反转清理、结束回到空闲
- 安全联锁：占用中不允许启动清理，清理中再次占用会立即停机进入保护态，满仓阻止清理
- 故障恢复：`BIN_FULL` 自动清除恢复，`PROTECT_TRIGGER` 通过 `SAFE_STOP` 释放后恢复，`CLEAN_TIMEOUT` 需要本地 `RESET`
- 本地展示：OLED 显示状态、故障、链路、满仓和保护标志
- 串口日志：关键状态切换、联锁拦截、故障进入、恢复动作都有明确日志
- finsh 命令：可查看状态、触发现有清理链路、执行本地恢复、进行 bench 级超时演示
- MQTT：最小状态上报，远程单次触发清理，请求断网时不影响本地控制闭环

## 系统架构概览

### 硬件与软件底座

- MCU：HC32F460
- RTOS：RT-Thread
- 本地外设：红外占用检测、称重、DHT11、电机、蜂鸣器、臭氧、OLED
- 联网方式：MQTT

### 线程与职责

```text
+------------------+        +--------------------+        +------------------+
| ReadSensor_Task  | -----> | StartControl_Task  | -----> | FSM + Motor Ops  |
| 采集温湿度/重量      | IPC    | 输入同步/事件分发/周期 tick |        | 执行动作/故障处理     |
+------------------+        +--------------------+        +------------------+
           \                                                    /
            \                                                  /
             +-------------------+    +-----------------------+
             | OLED / Serial /   |    | Mqtt_Task            |
             | finsh 本地可见性    |    | 最小状态上报/远程触发  |
             +-------------------+    +-----------------------+
```

### 为什么这样拆

- 传感采集、控制决策、联网通信彼此解耦，避免把控制逻辑绑死在网络状态上
- 状态机集中在 `app_logic/fsm.c`，让状态迁移、联锁和故障恢复具备清晰边界
- `app_logic/logic.c` 只负责输入整理、事件注入、本地状态摘要和 bench 命令，不重写 FSM 规则
- MQTT 保持最小职责，只负责上报和触发，不夺走本地控制权

## 状态机概览

当前显式状态如下：

- `IDLE`：空闲，可接受本地自动清理或远程单次触发
- `OCCUPIED`：检测到猫正在使用，禁止清理
- `LEAVE_CONFIRM`：离开确认窗口，避免猫刚离开就立刻启动
- `CLEAN_DELAY`：清理前延时窗口，给现场留出缓冲
- `CLEANING`：执行正转 / 反转清理
- `SAFE_STOP`：清理中遇到占用保护时的安全停机态
- `FAULT`：关键故障锁存态

### 典型主流程

```text
IDLE
  -> OCCUPIED
  -> LEAVE_CONFIRM
  -> CLEAN_DELAY
  -> CLEANING(FORWARD -> REVERSE)
  -> IDLE
```

### 设计原因

- 把“猫在不在”“是否可以清理”“是否进入故障”从 if-else 里剥离成显式状态
- 所有关键路径都有可打印、可观察的状态名，方便串口和 OLED 直接对应
- 便于后续继续增加更细粒度执行阶段，而不推翻已有结构

## 安全联锁概览

当前联锁遵循“先安全，后动作”的原则：

- 占用联锁：占用状态下禁止启动清理
- 运行中保护：`CLEANING` 期间若再次检测到占用，立即停机并转入 `SAFE_STOP`
- 满仓联锁：`bin_full=1` 时禁止启动清理，并进入 `BIN_FULL` 故障
- 本地恢复约束：`RESET` 在 `protect_active=1` 或 `bin_full=1` 时会被拒绝

这样设计的原因是，联锁不是“附加日志”，而是比清理动作优先级更高的硬约束。

## 故障恢复与关键告警概览

当前保留 3 个最关键、最能说明控制系统价值的故障：

- `BIN_FULL`
  - 触发：重量超过阈值，或清理前 / 清理中检测到满仓
  - 处理：阻止清理，进入 `FAULT`
  - 恢复：重量恢复后可自动清故障并回到 `IDLE/OCCUPIED`

- `PROTECT_TRIGGER`
  - 触发：清理过程中再次检测到占用
  - 处理：立即停机，进入 `SAFE_STOP`
  - 恢复：占用解除后自动恢复到 `OCCUPIED` 或 `LEAVE_CONFIRM`

- `CLEAN_TIMEOUT`
  - 触发：清理超时
  - 处理：停机，进入 `FAULT`
  - 恢复：需要本地 `litter_reset`

### 告警与可见性

- OLED 显示 `state / fault / mqtt / bin_full / protect`
- 串口输出 `[FSM] / [LOGIC] / [ACT] / [MQTT] / [STAT]` 关键日志
- `finsh` 可直接查看和触发 bench 演示命令
- MQTT 上报中包含 `state`、`fault_code`、`fault_text`、`mqtt_link`、`bin_full`、`protect_active`

## 本地展示与日志

### OLED

OLED 默认展示 5 行摘要：

- `W / U`：当前重量与使用次数
- `ST`：当前状态
- `F`：当前故障码和短故障名
- `MQ / BN / PT`：链路、满仓、保护标志
- `H / T`：温湿度

### 串口日志

为了演示清晰度，日志保持“关键变化才打印”：

- `[FSM]`：状态事件、联锁拦截、故障进入、恢复
- `[ACT]`：电机正转 / 反转 / 停机
- `[MQTT]`：在线 / 离线
- `[LOGIC]`：占用变化、满仓变化、reset / clean 请求
- `[STAT]`：状态摘要，仅在关键字段变化时输出

### finsh 命令

- `litter_status`
  - 打印 `state / fault / mqtt_link / bin_full / protect / occupied / weight / hum / temp`
- `litter_clean`
  - 通过现有 FSM 路径发起一次本地清理请求，便于脱网演示
- `litter_reset`
  - 请求本地恢复
- `litter_timeout`
  - 仅用于 bench 演示，在 `CLEANING` 期间注入现有 `CLEAN_TIMEOUT` 故障路径，便于稳定复现超时故障

说明：`litter_timeout` 是演示辅助命令，不改变正常控制逻辑，也不代表量产交互方式。

## 如何演示 6 个关键场景

更简洁的面试版清单见 [docs/demo_checklist.md](docs/demo_checklist.md)。

### 1. 正常清理闭环

前提：

- `state=IDLE`
- `fault=NONE`
- `bin_full=0`
- `protect=0`

推荐路径：

1. 执行 `litter_status`
2. 使用真实占用流程，或直接执行 `litter_clean`
3. 观察状态依次进入 `CLEANING`
4. 观察电机正转、反转、停机
5. 最终回到 `IDLE`

重点观察：

- OLED `ST`
- 串口 `[FSM] ENTER ...`
- `[ACT] motor forward / reverse / stop`

### 2. 占用保护停机

1. 先让系统进入 `CLEANING`
2. 清理过程中再次触发红外占用
3. 观察立即停机并转入 `SAFE_STOP`
4. 移开占用后，观察自动恢复

重点观察：

- `protect=1`
- `fault=PROTECT_TRIGGER`
- `SAFE_STOP`
- 电机立即停止

### 3. 清理超时 / 故障进入

推荐 bench 演示路径：

1. 先让系统进入 `CLEANING`
2. 执行 `litter_timeout`
3. 观察系统进入 `FAULT`
4. 再执行 `litter_reset` 验证恢复

重点观察：

- `fault=CLEAN_TIMEOUT`
- `state=FAULT`
- reset 前不会自动恢复

说明：这里复用的是现有超时故障处理链路，只是通过 finsh 做稳定复现，避免现场依赖不稳定的物理条件。

### 4. 满仓禁启

1. 让重量超过阈值
2. 执行 `litter_status` 确认 `bin_full=1`
3. 尝试 `litter_clean` 或等待自动清理路径
4. 观察清理被阻止并进入 `BIN_FULL`

重点观察：

- `bin_full=1`
- `[FSM] INTERLOCK block clean: bin full`
- `fault=BIN_FULL`

### 5. 断网本地可运行

1. 断开网络或让 MQTT 不可连接
2. 确认 `mqtt_link=0`
3. 通过真实占用流程或 `litter_clean` 发起清理
4. 观察本地状态机仍完整运行

重点观察：

- `[MQTT] link offline`
- 本地 `FSM` 和 `ACT` 仍正常工作

### 6. 故障恢复 / RESET 恢复

1. 先制造一个需要恢复的故障态
2. 确认当前 `protect=0` 且 `bin_full=0`
3. 执行 `litter_reset`
4. 观察系统返回 `IDLE` 或 `OCCUPIED`

重点观察：

- `fault` 清零
- 状态恢复可解释
- 本地恢复优先，不依赖云端

## 当前已知限制与后续演进方向

### 已知限制

- 清理执行当前仍是时间片式正反转，不是编码器 / 电流闭环控制
- `CLEAN_TIMEOUT` 的 bench 复现依赖演示命令，而不是物理卡滞检测链路
- 目前没有持久化事件历史，只保留串口实时日志和当前状态摘要
- MQTT 只保留最小状态上报和远程触发，没有复杂设备模型
- 人机界面以 OLED + 串口为主，不做复杂 App 展示

### 后续演进方向

- 加入更真实的执行器反馈，提升清理超时 / 卡滞检测可信度
- 增加告警历史缓存和事件追踪
- 在保持本地自治前提下，扩展更完整的云端设备模型
- 对状态机增加更细粒度运行指标，而不是增加无边界新功能

- 显式状态机

- 关键告警
